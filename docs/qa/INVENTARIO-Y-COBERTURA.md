Estado: `READY_FOR_REVIEW`. Fecha de auditoría: 2026-10-26 (America/Bogota).

Esta matriz se levantó mediante inspección estática de HEAD `f5f6671`, antes de validar los cambios de la auditoría. ## Fuentes y discrepancias documentales

- Leídos: `README.md`, `package.json`, `src/ui/`, `src/data/`, `src/domain/`, migraciones, pruebas SQL y E2E. Los documentos obligatorios `BUSINESS_RULES.md`, `PROJECT_STATE.md`, `BACKLOG.md`, `DECISIONS.md` y `LOCAL_SETUP.md` no estaban presentes en el árbol inicial; se consultaron en `git show 59219a8:docs/<archivo>` como antecedentes históricos. No son prueba de las reglas más recientes.
- README/antecedentes describen A+B+C+D y verificaciones de 2026-10-09/10. El árbol contiene correcciones FIN/QA posteriores, destinos explícitos de cobro, conciliación inicial, movimientos personales y compensación de préstamos. No se deben reutilizar los conteos de pruebas históricos como resultados actuales.
- El README menciona exportación `natillera-manager.abcd.v1`; la descarga JSON activa llama a `export_natillera_backup`, formato `natillera-manager.workspace.v3`, todos los ciclos del workspace. El CSV es un reporte, no una restauración. Auth, secretos y bytes privados no están en el JSON del navegador.
- El backlog histórico indica pendiente pantalla de reversos; el código actual incorpora `FinancialCorrections`, `UndoOperationButton`, `UndoPollaButton`, reversos de repartos y correcciones de ubicación. Eso no prueba que toda operación pueda anularse libremente: hay dependencias y guardas de dominio.
- Los identificadores de migración llegan a `20261107…` en la línea base aunque la fecha del cliente es 2026-10-26. Son identificadores de orden del código, no evidencia de fecha real de aplicación ni de que DEV/TEST las tengan aplicadas.
- No se encontró una acción de UI para cerrar/archivar el ciclo ni un método cliente equivalente a `close_cycle`. Las restricciones de fecha y publicaciones al cierre no equivalen a una implementación del archivo del ciclo. NAT-HU-007 sigue sin demostración de implementación en este inventario.

## Contratos SQL, seguridad y reconstrucción

- `financial_operations` registra tipo, fecha efectiva, payload e idempotencia; `ledger_entries` expresa ahorro, caja, cartera, bolsa, premios, administración y utilidades. Un saldo UI aislado no es fuente suficiente: contrastar dominio y partidas de TEST.
- `loan_payment_applications` materializa aplicación de capital/interés; `loan_schedule_progress` es vista `security_invoker`, no cronograma nuevo de importes. `loan_settlement_effects` permite reconstruir deudas compensadas por fecha. `fin03_member_mode_issues` expone incompatibilidades de modalidad con RLS.
- Triggers relevantes: balance de partidas/operación; inmutabilidad de identidades/documentos auditados; guardas de ciclo y polla cancelada; `settlement_close_satisfied_loan` cierra contratos totalmente compensados; `settlement_guard_loan_receipt` rechaza nuevo cobro de deuda compensada. Revisar también los wrappers renombrados por migraciones: la definición inicial de una RPC no determina la API vigente.
- RLS por workspace/admin y grants explícitos protegen lecturas; escrituras financieras se realizan mediante RPC transaccional. Probar anónimo, administrador de otro workspace y administrador propio. Las funciones `security definer` deben validar pertenencia y usar `search_path` explícito.
- Idempotencia: misma clave/carga devuelve mismo efecto; misma clave/carga distinta falla. Incluir doble clic, pérdida de respuesta, recarga/reintento, pago total y operación ya confirmada. Un `disabled` de React por sí solo no demuestra protección.
- `npm run test:rls` ejecuta la carpeta canónica `supabase/tests/database` mediante `scripts/run-sql-tests-local.mjs`, verifica API TEST `127.0.0.1:55421`, contenedor TEST y puerto DB `55422`, y exige plan TAP completo. La carpeta antigua `tests/database` contiene solo parte de las suites y no debe usarse para contar cobertura actual.
- La línea base de `npm run test:e2e` invocaba escritor dotenv/bootstrap y podía arrancar DEV por un argumento incorrecto. QA-05 lo corrigió con runtime en memoria y guardas TEST. `qa:functional:e2e` y la corrida completa de auditoría preparan sus propios fixtures sin dotenv. No basta un navegador local para demostrar aislamiento.

## Invariantes y oráculos de aceptación

| Invariante | Comprobación independiente requerida en TEST |
|---|---|
| Balance atómico | Por cada operación publicada/reverso, suma decimal de partidas = 0; ninguna fila huérfana o operación parcial tras rechazo. |
| Capital no se recobra | Principal menos pagos efectivos y compensaciones a fecha = saldo pendiente, nunca negativo. Aplicaciones por pago suman exactamente su capital/interés. |
| P011 sintético | Principal 500.000; interés mensual pactado 5%; dos intereses de 25.000 pagados; abono capital 200.000 deja 300.000 y 50.000 de interés histórico. La fila final puede conservar 525.000 originales solo si el pendiente 325.000 se distingue inequívocamente; «Pagar todo» usa cotización vigente, no capital original. El reverso restaura el estado exacto. |
| Política de interés | La modalidad contractual y las reglas SQL determinan interés exigible/cotizado. No reducir 25.000 a 15.000 ni modificar porcentaje por intuición; registrar decisión pendiente si el contrato no resuelve la política futura del abono parcial. |
| Destino real del cobro | Cobro 200.000 efectivo: efectivo +200.000 y banco sin cambio. Cobro bancario: cuenta elegida +200.000. Capital no incrementa utilidad; interés satisfecho se separa según regla vigente. |
| Caja/banco/disponible distintos | Liquidez total = banco + efectivo + pendiente; movimientos personales se excluyen de fondos colectivos; disponible descuenta obligaciones/reservas pertinentes. Traslados y ubicaciones conservan total. |
